# ToastManager fidelity corrections

`+[ToastManager sharedManager]` at `0x1c9b1c` passes global block `0x1062ca0` to `dispatch_once`. Its invoke pointer is `0x1c9ba4`. Unlike the receiver-based factories elsewhere in the package, this callback has no captured receiver. Instructions at `0x1c9bac` and `0x1c9bb0` load the concrete `ToastManager` class through `0x114ecd0`; the reference resolves to class metadata `0x114fc88`. Call `0x1c9bb4`, via thunk `0x1ca3a4`, reaches `_objc_alloc_init`.

The previous reconstruction used `[[self alloc] init]`, which made a subclass's first call instantiate that subclass. The source now uses `[[ToastManager alloc] init]`, preserving the original concrete target and once-only shared instance. No other `ToastManager` behavior changed in this bounded audit.

`python3 recovery/tools/verify_factory_audit.py` checks the original factory evidence, audits all 15 iOS method encodings, four properties and four relative ivar layouts, and compiles the complete `ToastManager.m` with a unique host-only UI boundary. Two fresh processes test subclass-first and base-first calls. Both verify the concrete result, zero subclass allocation/initialization calls, normal initialized state and shared identity across different subclasses. All 18 assertions pass with UndefinedBehaviorSanitizer. Before the correction, the subclass-first test failed at the concrete result assertion.

The existing full presentation fixture is unchanged by this fix. This focused proof does not exercise toast display or other manager methods. `recovery/tests/factory_audit_evidence.json` records the original binary hash and method/callback hashes; the broader bounded factory audit is documented in `recovery/tests/factory_audit.md`.

## Collection and dispatch lifecycle

The subsequent lifecycle audit corrected four additional differences. `init` calls `NSMutableArray array`. The class message method at `0x1c9c8c` allocates/initializes a concrete ToastView and registers it with the concrete ToastManager singleton before scheduling its strongly captured toast/text block. Only the eventual `showMessageWithText:isSuccess:` call runs on the main queue. It does not dispatch construction or ask a subclass for its singleton.

`registerToast:` retains the collection lock across the update call. Its original sync-enter, add, update and sync-exit calls are at `0x1c9e20`, `0x1c9e74`, `0x1c9e84` and `0x1c9e8c`. It neither requests the shared window nor unhides it. `unregisterToast:` similarly keeps its update within the lock, including when the nonnil toast was absent. `updateAllToasts` enumerates the live collection synchronously while holding its lock. It does not copy a snapshot or marshal to a different queue. Original mutation checking at `0x1ca12c` remains observable as Foundation's enumeration exception.

Run `python3 recovery/tools/verify_toast_manager_lifecycle.py`. The complete actual source passes 61 assertions, all 15 iOS method encodings, four properties and four relative ivar layouts. The fixture tests nested lock scope, duplicate/nil/absent registrations, caller-thread execution, live-enumeration mutation, concrete allocation, registration-before-dispatch and strong payload lifetimes. It intercepts only test queue/lock/UI boundaries. Compiler-generated lock calls are renamed in emitted LLVM IR, with both versions retained; no system runtime is interposed. The preceding source failed on its unexpected window access. The report pins the original image, 17 complete method/callback intervals and nine critical call targets. No original binary or device UI runs.
