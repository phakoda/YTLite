# Toast window, queue and setup fidelity

This audit covers `initialize`, `toastWindow` and its two global callbacks, `init`, `enqueueCommand:`, `processQueue`, `setupInterfaceWithText:progress:withStop:isStatus:isSuccess:withWait:`, observer handling, appearance callbacks and `cleanup`. The canonical original image remains SHA-256 `bdcc4d4ccaa5835d35bc97ccbdfc1c3dff514cb7161848265dcc0585f364c0ca`. The separate lifecycle audit covers presentation commands, countdown and hiding.

`initialize` at `0x1b9d50` calls the receiver's `toastWindow` synchronously only when the receiver is the concrete ToastView class. `toastWindow` at `0x1b9e04` always evaluates the same once token, with global block `0x1062a00` invoking `0x1b9e8c`. That block enumerates connected scenes for an active scene without a class filter. When none exists, it rereads `connectedScenes`, obtains `allObjects` and selects the first object. If that is nil, the once token is still consumed. The preceding reconstruction added a retry and extra scene-selection reads.

The window block allocates the concrete ToastWindow, assigns its screen frame and transparent root controller, unhides it, queues global block `0x1062a20` and then activates its four edge constraints. That queued block at `0x1ba69c` calls `makeKeyAndVisible`; it does not check or resign key status itself. ToastWindow's own implementation handles the subsequent key-status check.

The view's `init` at `0x1ba6d8` determines pad status before superclass initialization. Its condition is `idiom == pad || model contains iPad`, followed by a separate `model does not contain iPhone` check. Getter calls remain separate. The app source is the delegate's window directly; the toast source comes from the already-created global window. Neither lookup retries window creation or substitutes a key window from another scene.

Queue methods at `0x1bbd94` and `0x1bbe2c` operate on the calling thread. Enqueue copies the block, appends it and processes the queue. A nil command reaches Foundation's `addObject:` boundary. The process method checks only the animation flag and queue count, sets the flag, retains the first block, removes it and invokes it. There is no added main-thread scheduling.

Setup at `0x1bbf68` starts by registering the toast. It preserves prior completion/timer state, label font/alignment, custom action views, cached source and existing gesture recognizers. It replaces its constraint ivar references, activates three common constraints and then one positional constraint, without deactivating older constraints. The preceding reconstruction inserted resets, source retries and cleanup that changed repeated-use behavior. Cleanup at `0x1bfcdc` removes layer animations, invalidates and clears the stored timer, clears the two ignore flags, removes the view and observers, and unregisters it. It does not clear the completion block.

Observer setup at `0x1bf368` reads the default center separately for each registration and does not remove prior observers. Removal at `0x1bf6d4` also makes three separate center reads. The three notification methods update their ivars and call `updateLayout` synchronously. Good height still widens the original float-valued input. Added main-queue dispatch changed their timing and has been removed.

Both appearance methods set bottom, width and top constants in that order. The non-alpha method's block at `0x1befa0` sets the scale before reading the pinned state and switching constraints, then calls source layout. The alpha method at `0x1bf098` does not change hidden state; its animation block at `0x1bf1f4` sets alpha, switches constraints and applies the scale without a source-layout call. Its completion at `0x1bf2e4` invokes a captured completion regardless of the animation's finished flag.

Run `python3 recovery/tools/verify_toast_construction.py`. The fixture compiles the complete ToastView and ToastManager sources, compares all 47 ToastView method encodings, its property and 22 relative ivar layouts, and executes startup/setup behavior with synthetic UIKit. Six fresh processes cover active-scene, fallback-scene, absent-scene and background initialization, notifications and appearance. Runtime cases also cover model/idiom combinations, queue blocking/delivery, nil command, caller-thread execution and state preserved across repeated setup. The previous source fails on its extra scene reads, observer replacement and appearance visibility changes; `--before` and `--mode` rerun those retained cases. Current reports pin 19 original intervals, two global block pointers and all source/fixture inputs. Input hashes must remain unchanged throughout compilation and execution.

The fixture does not run a window server or the original binary. Its nil-scene and cached-source cases expose source decisions; they do not claim that UIKit tolerates every resulting nil anchor or repeated constraint installation. Those are original framework boundaries, not new compatibility promises.
